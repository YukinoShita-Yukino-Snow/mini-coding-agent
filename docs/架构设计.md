# 架构设计

## 一轮模型交互

```text
ContextManager
      |
      | 对话消息 + JSON 工具定义
      v
OpenAIChatClient -------> 模型 API
      |                       |
      | ModelReply            | 文本或 Function Tool Call
      v                       |
CodingAgent <-----------------+
      |
      | 工具名称 + JSON 参数
      v
ToolRegistry -> 本地工具 -> 结构化结果
      |
      +------ tool 消息 ------> ContextManager
```

`CodingAgent` 掌握循环控制权。模型响应中没有工具调用时，文本被视为最终结果；存在
工具调用时，Agent 保存完整 assistant 消息，执行对应本地工具，再添加带有
`tool_call_id` 的 tool 消息。这保证了多轮 Function Calling 消息关系合法。

## 组件职责

| 组件 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `Settings` | 从环境变量读取并校验配置 | 保存真实凭据 |
| `OpenAIChatClient` | 调用 API、重试并解析响应 | 执行本地工具 |
| `CodingAgent` | 控制决策循环和终止条件 | 直接访问文件系统 |
| `ContextManager` | 保存历史并控制上下文长度 | 使用服务端托管历史 |
| `ToolRegistry` | 派发已知工具并统一错误 | 执行未知工具 |
| 文件工具 | 在工作区内进行 UTF-8 文件操作 | 读取凭据和内部目录 |
| 命令工具 | 运行参数数组并捕获输出 | 调用 PowerShell、cmd 或 bash |

## 为什么使用原生 Tool Calling

Function Calling 返回明确的函数名和 JSON 参数，便于校验、派发和错误反馈。若直接
从模型自然语言或 Markdown 代码块中提取命令，普通说明和可执行内容之间容易产生
歧义，也难以保证 assistant-tool 消息配对。

## 上下文管理

项目使用字符数近似上下文预算，以兼容不同模型网关：

1. 始终保留系统提示和用户原始任务；
2. 优先截断过长的旧工具输出；
3. 仍然超限时，删除最早的完整 assistant-tool 轮次；
4. 始终保留最近一次工具轮次；
5. 必要内容仍无法放入预算时明确停止。

不能只删除某一条 tool 消息，因为孤立的 Tool Call 或没有对应调用的 Tool Result 会
形成非法 API 消息结构。

## 命令执行

`run_command` 使用 `subprocess.run(..., shell=False)`，模型必须把可执行程序和每个
参数分别放入数组。工作目录固定为目标项目，支持超时、输出截断和标准输入。

对于工作区内程序，工具会先把 `./app.exe`、`app.exe` 等形式安全解析为工作区绝对
路径；普通的 `python`、`git`、`g++` 仍由系统 PATH 查找。显式绝对路径若位于工作区
之外会被拒绝。子进程环境会移除名称中包含 API_KEY、TOKEN、SECRET 或 PASSWORD 的
变量，避免把模型凭据传给目标项目。

## 终止与错误处理

- 模型返回最终文本且没有工具调用：正常完成；
- 达到最大模型步骤数：停止并报告已完成工具数量；
- 连续三次工具失败：停止并报告最近错误和已有进度；
- 上下文无法安全压缩：停止并返回错误；
- 模型连接、超时、限流和服务端错误：有限次数指数退避重试；
- 用户按下 Ctrl+C：以退出码 130 结束。

工具参数或执行错误会作为结构化结果返回模型，使模型有机会根据观察自行修复。
